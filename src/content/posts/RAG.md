# RAG 检索增强生成全景指南：从基础原理到工程落地

## 一、RAG 基础概念

### 1.1 什么是 RAG？

**RAG (Retrieval-Augmented Generation，检索增强生成)** 是一种将信息检索技术与生成式大语言模型相结合的框架。核心思想是：在让 LLM 回答之前，先从知识库中检索出相关的上下文信息，"增强"其生成能力，使其产出更准确、更具时效性的回答。

### 1.2 为什么需要 RAG？

LLM 本身面临三个核心挑战，RAG 正是解决这些问题的有效方案：

- **知识时效性问题**：预训练 LLM 的知识固化在训练数据截止时间点。RAG 通过动态检索外部知识源，将最新上下文提供给 LLM。
- **私有数据访问**：企业内部的私有数据无法被公开 LLM 直接访问。RAG 在不泄露全部数据的前提下，基于企业自身知识进行回答。
- **对抗模型幻觉**：LLM 有时会产生"幻觉"，编造不符合事实的信息。RAG 通过提供有据可查的参考文本，引导模型基于检索证据回答，降低幻觉概率。

> **注意**：RAG 不能彻底消除幻觉。检索错误、上下文噪声、引用错配都可能导致错误答案。生产级 RAG 还需要引用校验、答案评估、拒答机制和人工反馈闭环。

### 1.3 RAG 工作原理

RAG 的工程链路分为两个阶段：

**离线索引阶段**：

```
原始文档 -> 文档清洗 -> 文档拆分(Chunking) -> Embedding 向量化 -> 存入向量数据库
```

**在线检索生成阶段**：

```
用户查询 -> Query 向量化 -> 向量相似度检索 -> 上下文构建 -> LLM 生成答案
```

核心角色分工：

| 环节 | 做什么 | 关键点 |
| --- | --- | --- |
| 文档拆分 | 将文档切分成语义完整的片段 | Chunk 大小、重叠度、切分策略 |
| Embedding | 将文本转为高维稠密向量 | 模型选型决定语义召回上限 |
| 向量检索 | 在向量空间中找最相似的 Top-K | 索引算法、相似度度量 |
| 上下文构建 | 将检索片段+原始问题+指令组装 | 去重、排序、压缩、引用 |
| LLM 生成 | 基于检索证据生成回答 | Prompt 限定证据边界 |

### 1.4 RAG 的演进阶段

| 阶段 | 典型链路 | 核心特点 |
| --- | --- | --- |
| Naive RAG | 文档切块 → Embedding → Top-K 检索 → LLM 生成 | 最基础，适合 Demo |
| Advanced RAG | Query Rewrite / HyDE → 混合检索 → Rerank → 上下文压缩 → LLM 生成 | 解决召回不准、噪声和排序问题 |
| Modular RAG | 检索器、重排器、压缩器、路由器可插拔组合 | 按场景动态路由，适合生产系统 |

### 1.5 RAG vs 微调 vs 长上下文

| 维度 | RAG | 微调（Fine-tuning） | 长上下文 |
| --- | --- | --- | --- |
| 知识更新 | 更新知识库即可 | 需重新训练 | 需要重新输入 |
| 幻觉控制 | 可引用原文溯源 | 模型仍可能编造 | 可能被中间噪声干扰 |
| 适合场景 | 知识密集型问答 | 风格适配、格式控制 | 单篇长文档深度分析 |
| 主要风险 | 检索不到、召回噪声 | 过拟合、知识过期 | Token 成本高、注意力稀释 |

**一句话总结**：知识变动频繁、需要引用来源，优先 RAG；输出风格和任务行为不稳定，考虑微调；长上下文窗口解决"能不能放进去"的问题，RAG 解决"该放什么进去"的问题。实际项目中通常组合使用。

## 二、Embedding 与向量相似度

### 2.1 Embedding 是什么？

Embedding 是把文本映射到高维稠密向量空间，让语义相近的文本在向量空间中距离更近。维度通常是 768、1024、1536、3072 等。维度越高，表达信息越丰富，但存储和计算成本也越高。

常见 Embedding 模型：

| 类型 | 代表模型 | 适合场景 |
| --- | --- | --- |
| 闭源 API | OpenAI text-embedding-3-small/large、Cohere Embed | 开箱即用、多语言、少运维 |
| 开源模型 | BGE 系列、GTE 系列、E5 系列 | 数据不出内网、私有化部署 |

> **选型建议**：不要只看 MTEB 榜单排名，要用自己的业务问题评测召回率、相关性和延迟。

### 2.2 向量相似度怎么计算？

| 度量方式 | 核心含义 | 特点 |
| --- | --- | --- |
| 余弦相似度（Cosine Similarity） | 看两个向量方向是否一致 | 对向量长度不敏感，RAG 最常用 |
| 内积（Inner Product） | 两个向量对应维度乘积之和 | 向量已归一化时，与余弦排序等价 |
| 欧氏距离（L2 Distance） | 看两个点在空间中的绝对距离 | 对向量幅度更敏感 |

**面试回答模板**：RAG 关注的是语义方向是否接近，而不是向量长度本身；余弦相似度对长度不敏感，更适合文本语义检索。实践中最容易踩的坑是：**查询运算符必须和索引 operator class 一致**，否则数据库可能无法使用向量索引。

## 三、文档处理与 Chunking 策略

### 3.1 文档处理链路

```
文件上传 -> 格式校验 -> Layout 解析 -> 清洗去噪 -> Chunking 切分 -> Metadata 绑定 -> 向量入库
```

每个环节的核心风险：

| 环节 | 典型问题 | 最终影响 |
| --- | --- | --- |
| Layout 解析 | PDF 多栏、表格合并单元格、页眉页脚 | 结构丢失、上下文错位 |
| 清洗去噪 | 乱码、特殊字符、重复空行 | 噪声入索引、Embedding 失真 |
| Chunking | 语义截断、上下文断裂 | 召回不准、答案残缺 |
| Metadata | 没保存来源、页码、版本、权限 | 无法过滤、无法引用 |

**核心原则**：RAG 的瓶颈通常不在检索层，而在文档进入索引之前的那段管线。数据处理做不好，换什么 Embedding 模型都白搭。

### 3.2 Chunking 策略对比

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定长度切分 | 按字符/Token 硬切 | 简单、行为可预测 | 不懂语义边界 |
| 递归字符切分 | 按换行、句号、空格逐层切 | 保留部分层级结构 | 对复杂文档仍有偏差 |
| 语义切分 | 用 Embedding 判断句子相似度聚类 | 按意义切分 | 容易产生超小块，成本高 |
| 按文档结构切 | 按标题层级、页面、代码结构切 | 天然语义边界 | 依赖文档结构规范 |
| Parent-Child Chunk | 小块用于检索，大块用于生成 | 兼顾召回精度和上下文 | 索引存储量增加 |

### 3.3 Parent-Child Chunk 模式

一个高频痛点是：小块召回准但上下文残缺，大块保留完整但召回噪声大。

做法是：
1. 把文档切成 300 Token 左右的小块，用于向量检索
2. 每个小块都挂载到一个 1200 Token 的父段落上
3. 检索时先命中小块，再把对应父段落放入上下文

这种模式在长文档、教程、政策解读、故障手册等场景下效果明显。

### 3.4 语义丢失与应对

语义丢失的本质是：**切分破坏了原始文本的上下文依赖关系，而 Embedding 模型只能看到切分后的局部窗口**。

常见应对策略：

- **增加语义入口**：给每个 Chunk 生成摘要和问题变体一起入索引，增加命中概率
- **保留层级元数据**：在 Metadata 里记录章节路径、父子标题、段落编号
- **Late Chunking**：先把完整文档通过 Transformer 编码，再在 Embedding 空间做切分和池化
- **Contextual Chunking**：用另一个 LLM 分析文档结构，生成切分建议

### 3.5 分层校验策略

| 校验层 | 检查内容 | 失败处理 |
| --- | --- | --- |
| 格式校验 | 扩展名、MIME 类型、文件大小 | 拒绝入库，通知上传者 |
| 解析校验 | 内容是否为空、乱码率、长度合理性 | 人工处理队列或备用解析器 |
| Chunking 校验 | 块大小分布、边界合理性、截断问题 | 改用固定长度切分兜底 |

### 3.6 多模态内容处理

**图片内容**三种处理路径：
- **CLIP 向量化 + 原始图片回传**：适合自然图片，对截图和图表理解有限
- **MLLM 描述 + 文本检索**：用多模态大模型生成图片文本描述，描述入索引
- **多向量索引（Multi-Vector Retriever）**：摘要用于检索，原文用于生成

**表格处理**：优先将表格转为 Markdown 表格格式或结构化 JSON，保留列与列之间的关联关系。

**核心思路**：摘要用于检索，原文用于生成。向量索引里存的是结构化描述，原始素材存在 docstore，检索命中后再取出交给 LLM 综合。

## 四、向量数据库与索引算法

### 4.1 为什么需要向量数据库？

当 Chunk 数量达到几十万、百万级时，没有专门向量索引的数据库只能全表扫描（O(n)），延迟秒级——完全不可接受。

**ANN 近似检索**：通过图导航、空间划分或量化等方式减少距离计算次数，在召回率、延迟和资源消耗之间做工程权衡。

| 指标 | 暴力搜索 | ANN 索引检索 |
| --- | --- | --- |
| 检索方式 | 全量计算距离 | 只搜索候选集 |
| 召回率 | 理论 100% | 取决于索引类型和参数 |
| 延迟 | 数据量越大越慢 | 通常显著更低 |

### 4.2 主流向量索引算法

| 算法 | 原理 | 核心优势 | 主要劣势 |
| --- | --- | --- | --- |
| Flat（暴力搜索） | 遍历所有向量 | 100% 准确 | 数据量大时很慢 |
| HNSW（图索引） | 分层导航小世界图 | 查询快，召回率高 | 内存消耗大 |
| IVFFLAT（倒排聚类） | 聚类 + 倒排索引桶 | 内存友好，构建快 | 召回率略低 |
| IVF-PQ（乘积量化） | 聚类 + 向量极致压缩 | 支持海量数据 | 精度损失较大 |

### 4.3 HNSW vs IVFFLAT

| 特性 | HNSW | IVFFLAT |
| --- | --- | --- |
| 底层原理 | 层次化小世界图结构 | 聚类 + 倒排桶结构 |
| 查询速度 | 通常更快，召回更稳定 | 取决于 lists 和 probes |
| 内存消耗 | 较高（原始向量 + 图指针） | 通常低于 HNSW |
| 构建速度 | 较慢 | 通常更快 |
| 适用场景 | 高召回、低延迟 | 内存和构建速度优先 |

**HNSW 调优参数**：

| 参数 | 常见范围 | 作用 |
| --- | --- | --- |
| `m` | 8-64 | 每个节点的最大连接数 |
| `ef_construction` | 64-256+ | 索引构建时的搜索范围 |
| `ef_search` | 40-200+ | 查询时搜索范围，直接影响召回-延迟平衡 |

### 4.4 向量数据库选型

| 方案 | 适合规模 | 核心优势 |
| --- | --- | --- |
| PostgreSQL + pgvector | < 100 万向量 | 一套数据库搞定，运维简单，事务一致 |
| Elasticsearch / OpenSearch | 混合检索优先 | 无缝结合 BM25 + 向量语义搜索 |
| Milvus / Qdrant / Weaviate | 百万到十亿级 | 专业向量检索能力，分布式扩展 |
| Pinecone / Zilliz Cloud | 任意规模 | 全托管，低运维，快速上线 |

**选型决策逻辑**：
- 已有 PostgreSQL，数据量小于百万 → **pgvector**
- 已有 ES，强依赖混合检索 → **ES 向量检索**
- 数据量千万级以上 → **Milvus / Qdrant / Weaviate**
- 不想自运维 → **Pinecone / Zilliz Cloud**

### 4.5 pgvector 实践要点

```sql
-- HNSW 索引创建
CREATE INDEX idx_document_embedding_hnsw
ON document_chunk
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- IVFFLAT 索引创建
CREATE INDEX idx_document_embedding_ivfflat
ON document_chunk
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- 查询时调节召回
SET hnsw.ef_search = 100;
SET ivfflat.probes = 10;
```

**关键注意**：
- 查询运算符必须与索引 operator class 一致，否则不走索引
- 大量删除/更新后需 `VACUUM`、`REINDEX`
- HNSW + WHERE 过滤可能导致 Top-K 不足，需要增大 `ef_search` 或使用预过滤

## 五、RAG 优化实践

### 5.1 优化框架

RAG 本质上是一条证据加工流水线，一环出问题就会传染下游：

```
文档解析 → Chunk 切分 → Metadata 标注 → 混合召回 → Rerank 重排 → 上下文压缩 → LLM 生成 → 答案评估
```

判断标准（按优先级）：
1. 正确证据有没有被召回？
2. 正确证据有没有排在足够靠前的位置？
3. 放进上下文的内容是否足够少、足够准？
4. 模型有没有严格基于证据回答？

### 5.2 Hybrid Search 混合检索

向量检索擅长语义相似，BM25 擅长精确词匹配，两者是互补关系：

| 查询类型 | 向量检索表现 | BM25 表现 | 建议 |
| --- | --- | --- | --- |
| "如何取消订阅" | 能匹配"关闭自动续费" | 可能匹配不到 | 保留向量召回 |
| "错误码 E1027" | 可能召回泛化故障 | 精确命中错误码 | 必须保留关键词召回 |
| "ABX-4421 型号参数" | 容易找相似型号 | 精确命中 SKU | 必须保留关键词召回 |

Hybrid Search 常见做法：向量检索 + BM25 两路召回，用 RRF（Reciprocal Rank Fusion）或归一化加权分数合并，去重后进入 Rerank。

### 5.3 Query Rewrite 查询改写

用户问题通常不是为检索系统写的。Query Rewrite 的目标是：**不改变用户意图，把问题改写成更适合召回的表达**。

| 策略 | 适用场景 | 例子 |
| --- | --- | --- |
| 规范化改写 | 口语化、缩写、上下文缺失 | "钱能退吗" → "退款政策、退款条件、退款流程" |
| Multi-Query | 表达可能有多种说法 | 同时检索"取消订阅""关闭自动续费""停止会员" |
| HyDE | 查询太短，与文档形态差异大 | 先生成假设答案，用假设答案向量检索真实文档 |
| Query Decomposition | 问题包含多个子问题 | 把复杂问题拆成子问题分别检索再汇总 |
| Self-Query | 问题里包含过滤条件 | 从"查 2025 年 Java 相关政策"提取年份和类别过滤 |

> **关键**：Query Rewrite 必须保留原始问题，让原始 query 和改写 query 一起召回再融合。

### 5.4 Rerank 重排

向量相似度更像"这两段话语义接近吗"，Rerank 更像"这段话能不能回答这个问题"。

推荐链路：
1. Metadata 预过滤
2. Hybrid Search 粗召回 30-100 条
3. 去重和相邻片段合并
4. Rerank 选出 5-10 条
5. 上下文压缩后放入 Prompt

**分层召回策略**：
- `recall_top_k`：粗召回候选池（30-100）
- `rerank_top_n`：重排后保留（5-10）
- `context_top_n`：最终进入上下文（3-6）

### 5.5 上下文工程

**上下文不是越多越好**。无关上下文会稀释注意力、增加延迟、提高 Token 成本。

上下文压缩常见方式：
- **选择性抽取**：只保留和问题相关的原句
- **查询相关摘要**：把长片段压成围绕问题的摘要
- **结构化抽取**：抽取字段、条件、结论、例外

上下文排序策略：最相关证据放前面，同文档相邻片段保持原始顺序，标注版本和来源，低置信度证据不和高置信度证据混排。

**Prompt 必须明确**：
- 只基于给定上下文回答
- 上下文不足时明确说"无法判断"
- 每个关键结论附来源
- 不要把相似文档当成当前版本事实

### 5.6 RAG 评估体系

**检索指标**：Hit Rate@K、MRR（Mean Reciprocal Rank）、Context Recall、Context Precision

**生成指标**：Faithfulness（忠实度）、Answer Relevancy、Citation Accuracy

**工程指标**：P95 延迟、Token 消耗、重排耗时、缓存命中率

> 建议建立最小评估集（50-100 条），覆盖高频问题、失败问题、精确匹配问题、拒答问题。每次改动都拿同一批问题跑回放，比较各项指标。

### 5.7 排查路径

线上 RAG 效果差时，按以下顺序排查：

1. **正确证据有没有进入候选池？** → 查文档入库、解析、Chunking、Metadata 过滤、Query Rewrite
2. **正确证据在候选池但没进上下文？** → 查 Rerank 模型、分数融合、`rerank_top_n` 设置
3. **上下文正确但答案错误？** → 查 Prompt 约束、证据冲突、多跳推理需求、生成模型
4. **建立回归测试** → 每修一个失败样本，加入评估集，持续沉淀

## 六、知识库更新策略

### 6.1 更新的核心目标

- **动态性**：文档变了，索引能及时跟上
- **准确性**：更新后召回的文档与源文档一致
- **一致性**：向量库、元数据库、全文索引之间数据一致
- **可回滚**：出故障能快速切回健康状态
- **可观测**：更新过程可监控、可定位

### 6.2 Embedding 模型一致性

**第一铁律：索引时用的 Embedding 模型，必须和查询时用的模型完全一致。**

不同模型的向量空间完全不同。工程上必须把 Embedding 模型版本写入元数据：

| 字段 | 说明 |
| --- | --- |
| `embedding_model` | 模型名称，如 `text-embedding-3-large` |
| `embedding_model_version` | 模型版本号 |
| `embedding_dimension` | 向量维度 |

模型升级推荐流程：新索引用新模型全量重建 → 新旧索引并行运行 → 确认稳定后通过索引别名切换 → 保留旧索引用于回滚。

### 6.3 元数据设计

每个 Chunk 至少携带：

- `doc_id` / `chunk_id`：唯一标识
- `content_hash`（SHA-256）：判断内容是否变化，实现增量更新的核心
- `version_id`：文档修改版本号
- `is_deleted`：软删除标记
- `tenant_id` / `acl`：多租户和权限控制
- `source_id` / `source_type`：来源追溯
- `section_path` / `title`：层级元数据
- `created_at` / `updated_at`：时间过滤

### 6.4 新增、修改、删除文档

**新增**：解析 → 切分 → 计算 content_hash → 检查去重 → Embedding → 写入三端（向量库、元数据库、全文索引）。

**修改**：核心做法是「软删除旧版本 + 写入新版本」。**最高频踩坑是只写新向量，不删旧向量**——文档改了 10 版，向量库存了 10 个版本，用户可能召回第 3 版的过时内容。

**删除**：软删除（`is_deleted = true`）→ 延迟物理删除（如 30 天后）→ 清理缓存。删除必须三端一致：向量库、元数据库、全文索引同步处理。

### 6.5 增量更新 vs 全量重建

| 维度 | 增量更新 | 全量重建 |
| --- | --- | --- |
| 触发条件 | 文档变更事件 | 定时任务或手动触发 |
| 覆盖范围 | 仅变化的文档 | 整个知识库 |
| 计算成本 | 低 | 高 |
| 更新延迟 | 低，可近实时 | 高，可能需数小时 |
| 适用场景 | 日常变更 | 模型升级、策略调整、故障恢复 |

**生产推荐策略**：实时增量 + 定期全量重建 + 事件驱动的紧急重建。每周或每月执行一次全量重建，清理残留数据、修正累积误差。

### 6.6 可靠性保障

**幂等更新**：利用数据库唯一约束（`doc_id + chunk_id`）保证幂等，而不是"先查再写"。并发场景下，数据库拒绝重复插入是唯一可靠的幂等保证。

**乱序事件处理**：每个事件携带 `version`、`updated_at`，写入前校验只允许新版本覆盖旧版本，旧事件到达直接丢弃。

**重试机制**：指数退避重试 + 死信队列兜底。瞬时错误（网络超时）重试，永久错误（格式错误）直接入死信队列。

**回滚机制**：索引别名切换是最简单可靠的回滚方式——新索引有问题，别名指回旧索引，前提是旧索引没被提前删除。

**灰度发布**：先更新 10% 文档或先让 5% 用户使用新索引，监控召回率、延迟、用户负面反馈率，任何指标异常立即停止。

## 七、GraphRAG：知识图谱增强检索

### 7.1 GraphRAG 是什么？

GraphRAG 在传统向量检索之外引入知识图谱，把文档中的实体、关系和结构化上下文显式建模。检索时除了召回相似片段，还会沿着图关系收集证据。

| 维度 | 传统向量 RAG | GraphRAG |
| --- | --- | --- |
| 检索对象 | 文本 Chunk | 实体、关系、路径、社区摘要、原文片段 |
| 核心能力 | 语义相似度召回 | 关系推理、图遍历、全局主题聚合 |
| 适合问题 | 局部事实问答 | 多跳关系问答、跨文档归纳、复杂业务分析 |
| 构建成本 | 中等 | 高（抽取、消歧、建模、评测） |
| 可解释性 | 依赖引用片段 | 可展示节点、关系、路径和来源 |

> **向量 RAG 像在图书馆按语义找几页相似内容。GraphRAG 像先整理出人物关系图和事件时间线，再沿着关系线索找证据。**

### 7.2 传统向量 RAG 的局限性

1. **Chunk 是信息孤岛**：不同章节的信息被切分散，向量检索不知道它们在业务上属于同一个对象
2. **不擅长多跳推理**：无法沿着 "系统 → 负责人 → 复盘 → 链路" 这样的关系路径扩展证据
3. **全局性问题很难靠 Top-K 回答**：需要对整个语料做聚合归纳，而非只找最相似的几段话

### 7.3 GraphRAG 核心概念

**知识图谱**：用"节点 + 边"表达知识的结构。节点表示实体（系统、人、组织、事件），边表示关系（依赖、影响、负责），属性记录补充信息（时间、版本、来源）。

**实体**：GraphRAG 的最小业务对象。可以是业务系统、技术组件、规范条款、风险主题、项目事件。

**关系**：GraphRAG 的灵魂。把关系的类型和方向显式化。有了关系，检索就可以沿着路径扩展：从一个实体找邻居、从一类关系找上下游、从一个事故找影响范围。

**社区发现**：用 Leiden 等算法找出图中连接更紧密的节点组，为每个社区生成摘要。查询全局问题时，先看社区摘要而非遍历所有文档。

### 7.4 全局检索 vs 局部检索

| 检索模式 | 适用场景 | 核心机制 |
| --- | --- | --- |
| Basic Search | 普通事实查询 | 标准 Top-K 向量检索 |
| Local Search | 围绕特定实体的问答 | 从实体邻居和关联概念扩展 |
| DRIFT Search | 实体焦点 + 跨社区关联 | 局部扩展 + 社区摘要上下文 |
| Global Search | 全局主题归纳 | 社区摘要 Map-Reduce |

**局部检索**：从实体出发，沿着邻居、关系路径、原文片段扩展上下文。适合"订单中心依赖哪些服务"。

**全局检索**：先利用社区摘要做聚合，再让 LLM 归纳和排序。适合"这批报告里反复出现的风险主题是什么"。

### 7.5 GraphRAG 的构建和查询流程

**构建阶段**：
```
文档解析 → 文本切分 → 实体抽取 → 关系抽取 → 图谱归一（消歧） → 社区发现 → 摘要生成 → 索引入库
```

**查询阶段**：最关键的是查询路由——根据问题类型选择不同的检索模式。简单问题用向量检索更便宜更快，不要所有问题都走 GraphRAG。

### 7.6 Neo4j GraphRAG 与其他实现

| 实现路线 | 核心思路 | 适合情况 |
| --- | --- | --- |
| Neo4j GraphRAG | 图数据库 + 向量索引 + Cypher 查询 | 已有业务关系，结构化查询需求强 |
| LangChain + Neo4j | GraphCypherQAChain 转自然语言为 Cypher | 已在 LangChain 生态 |
| LlamaIndex PropertyGraphIndex | 从 Chunk 中抽取实体关系构建属性图索引 | 已在 LlamaIndex 生态 |
| FalkorDB GraphRAG SDK | 支持 OpenCypher、全文索引、向量相似度的图数据库 | 探索 Neo4j 之外的图数据库 |
| 轻量自研图谱 + 向量库 | 业务表保存核心实体关系，向量库负责召回 | 第一版验证 GraphRAG 价值 |

其中 **VectorCypherRetriever**（向量检索找起点 + Cypher 查询扩展上下文）和 **Text2Cypher**（LLM 生成 Cypher 精确查询）是最有工程价值的模式。

### 7.7 GraphRAG 落地难点

1. **实体消歧**：同一实体的多个名字需要术语词典、别名表、规则匹配和人工校验
2. **关系方向**："A 依赖 B"和"B 依赖 A"只差一个方向，工程含义完全相反，建议给关系加 source_doc_id、source_span、confidence 等字段
3. **社区摘要成本**：构建阶段需要大量 LLM 调用做抽取和摘，索引成本明显高于向量 RAG
4. **增量更新复杂**：更新一篇文档可能影响实体、关系、社区、摘要、向量索引、权限索引
5. **权限过滤更复杂**：用户能看某个节点但能不能看它的邻居？社区摘要是否混入无权限信息？

### 7.8 分阶段落地路径

1. **阶段一**：做好向量 RAG 基线（文档解析、混合检索、Rerank、权限过滤）
2. **阶段二**：收集关系型失败案例，明确判断是否需要 GraphRAG
3. **阶段三**：从轻量图谱开始，只抽取核心实体和高价值关系
4. **阶段四**：引入社区发现和全局检索
5. **阶段五**：演进为按问题类型动态路由的 Hybrid RAG 架构

> **务实判断标准**：如果 RAG 失败原因只是"没搜到那段话"，先优化检索；如果失败原因是"搜到了很多话但系统不理解它们之间的关系"，再考虑 GraphRAG。

## 八、核心面试问答速答

**Q: RAG 和传统搜索引擎有什么区别？**
A: 传统搜索是"相关性排序器"，返回文档列表用户自己读。RAG 是"信息综合器"，将检索到的多个知识碎片喂给 LLM 进行逻辑归纳和跨文档整合，直接输出答案并附引文标注。

**Q: RAG 和微调怎么选？**
A: RAG 解决"模型不知道新知识/私有知识"的问题，微调解决"模型不会按你的方式说话或做事"的问题。知识变动频繁、需要引用来源优先 RAG；输出风格和任务行为不稳定考虑微调；既要领域表达又要实时知识就两者结合。

**Q: 为什么 RAG 常用余弦相似度？**
A: 文本语义检索更关心方向是否接近，而不是向量长度本身。余弦距离对长度不敏感，更适合判断语义相似。

**Q: HNSW 和 IVFFLAT 的区别？**
A: HNSW 是图索引，查询快、召回高但内存消耗大；IVFFLAT 是聚类倒排，内存友好、构建快但召回率略低。前者适合低延迟高召回场景，后者适合内存和构建成本敏感场景。

**Q: RAG 的"幻觉"问题怎么解决？**
A: RAG 本身通过提供参考文本降低幻觉概率，但不能彻底消除。需要配合引用校验、答案评估、拒答机制（证据不足时拒答）、人工反馈闭环。

**Q: 长上下文窗口会取代 RAG 吗？**
A: 不会。知识库规模远超单次窗口、Token 成本不可忽视、无关内容越多信噪比越低、权限隔离更难靠"全塞进去"解决。更现实的路线是先用 RAG 筛出高质量证据，再用长上下文做深度分析。

**Q: 向量数据库怎么选？**
A: 小于 100 万向量 + 已有 PG → pgvector；已有 ES → ES 向量检索；千万级以上 → Milvus/Qdrant/Weaviate；不想自运维 → Pinecone/Zilliz Cloud。

**Q: GraphRAG 和普通 RAG 有什么区别？**
A: 普通向量 RAG 检索文本 Chunk，适合局部事实问答；GraphRAG 把实体和关系显式建模成知识图谱，不仅能语义检索，还能沿图关系做多跳推理和社区摘要聚合。代价是构建成本、维护复杂度和权限控制难度显著更高。

## 九、总结

RAG 是当下企业级 AI 应用最核心的技术栈之一。从 Naive RAG 到 Advanced RAG 再到 GraphRAG，本质上是检索对象从"文本片段"不断升级到"结构化知识"的过程。

核心经验：
1. **数据决定上限**：文档解析、清洗、Chunking 是地基，地基歪了后面全是错的
2. **混合检索是生产默认项**：向量负责语义，BM25 负责精确匹配，两者互补
3. **Rerank 决定证据顺序**：粗召回要全，重排要准，上下文要精
4. **向量数据库选型看规模**：小规模 pgvector 足够，大规模上专业方案
5. **知识库更新是系统工程**：增量更新是日常，全量重建是周期性健康维护
6. **GraphRAG 补关系推理短板**：但成本更高，应先做好向量 RAG 基线再按需引入
7. **评估闭环是唯一可信的优化依据**：没有测试集和回放的优化都是玄学
